# Conditioned Profile

This project provides a command-line tool that is used to generate and maintain
a collection of Gecko profiles.

Unlike testing/profiles, the **conditioned profiles** are a collection of full
Gecko profiles that are dynamically updated every day.

Each profile is created or updated using a **scenario** and a
**customization**, and eventually uploaded as an artifact in TaskCluster.

The goal of the project is to build a collection of profiles that we can use in
our performance or functional tests instead of the empty profile that we
usually create on the fly with **mozprofile**.

Having a collection of realistic profiles we can use when running some tests
gives us the ability to check the impact of user profiles on page loads or
other tests.

A full cycle of how this tool is used in Taskcluster looks like this:

For each combination of scenario, customization and platform:

- grabs an existing profile in Taskcluster
- browses the web using the scenario, via the WebDriver client
- recreates a tarball with the updated profile
- uploads it as an index artifact into TaskCluster - maintains a changelog of each change

It's based on the Arsenic webdriver client <https://github.com/HDE/arsenic>

The project provides two **Mach** commands to interact with the conditioned
profile:

- **fetch-condprofile**: downloads a conditioned profile and deecompress it
- **run-condprofile**: runs on or all conditioned profiles scenarii locally

# How to download a conditioned profile

From the root of your Firefox checkout, run:

```
$ ./mach fetch-condprofile
```

This will grab the latest conditioned profile for your platform. But
you can also grab a specific profile built from any scenario or platform.

You can look at all the options with --help

# How to run a conditioned profile

If you want to play a scenario locally to modify it, run for example:

```
$ ./mach run-condprofile --scenario settled --visible /path/to/generated/profile
```

The project will run a webdriver session against Firefox and generate the profile.
You can look at all the options with --help

# Architecture

The conditioned profile project is organized into webdriver **scenarii** and
**customization** files.

## Scenarii

Scenarii are coroutines registered under a unique name in condprof/scenarii/\_\_init\_\_.py.

They get a **session** object and some **options**.

The scenario can do whatever it wants with the browser, through the webdriver session
instance.

See Arsenic's [API documentation](https://arsenic.readthedocs.io/en/latest/reference/session.html) for the session class.

Adding a new scenario is done by adding a module in condprof/scenarii/
and register it in condprof/scenarii/\_\_init\_\_.py

A scenario module can also declare these module-level constants:

| Constant | Purpose |
|---|---|
| `DEFAULT_CUSTOMIZATION` | Base customization used when `--customization` is a JSON override without a `customization` key |
| `PROXY_MODE` | Start a mozproxy proxy before the scenario runs: `"intercept"`, `"playback"` or `"record"` |
| `PLAYBACK_VERSION` | mitmproxy version to use when `PROXY_MODE` is set |
| `addons` | mitmproxy addon instances served in `intercept` mode |
| `PLAYBACK_FILES` | Recordings to replay in `playback` mode |
| `RECORDING_FILE` | Zip file to write in `record` mode |

### Proxy modes

Scenarios that browse to real websites, like `full` or `settled`, run
without a proxy. A scenario that needs one declares `PROXY_MODE` and
`PLAYBACK_VERSION`, and the runner starts mozproxy before the first
step and stops it after the last one. The browser is started with
`acceptInsecureCerts` in `intercept` mode so the mitmproxy certificate
is accepted.

- **intercept** serves responses generated by the scenario module's own
  mitmproxy addon, listed in `addons`. This is how scenarios that
  navigate to synthetic hosts such as `test-*.org` work.
- **playback** replays the recordings listed in `PLAYBACK_FILES`.
- **record** records live traffic into `RECORDING_FILE`.

The `proxy_mode` and `playback_version` arguments of `Runner` override
the module constants.

On desktop, mozproxy points Firefox at the proxy through a `policies.json`
next to the binary. On Android, condprof sets the `network.proxy.*` prefs
in the GeckoView configuration and opens an `adb reverse` for the proxy
port, so the device reaches the proxy running on the host. mozproxy also
installs its certificate into the profile with `certutil`: in automation
(`run_local=False`) the tool comes from the hostutils tooltool manifest,
locally `MOZ_HOST_BIN` must point at a desktop build's `dist/bin`, as for
`mach raptor` on Android.

## Customization

A customization is a configuration file that can be used to set some
prefs in the browser and install some webextensions.

Customizations are JSON files. The built-in ones live in
`condprof/customization/`, but a customization file can live anywhere
in the tree (e.g. under your component's test directory) as long as
callers pass a full or relative path instead of a bare name.

Customization files provide the following keys:

- **name**: the name of the customization
- **addons**: a mapping of add-ons to install.
- **prefs**: a mapping of prefs to set
- **scenario**: scenario options (see below)
- **keep_cache**: when `true`, the browser cache directories (`cache/`
  and `cache2/`) are kept in the archived profile. Default is `false`.
- **delete_after_build**: a list of glob patterns, relative to the
  profile, for files or directories to delete once every step has run.

A scenario step may also carry its own **delete_after_build** option,
which is applied in addition to the customization-level list. Both are
consumed by condprof and never passed to the scenario function.

### Scenario options

The **scenario** key accepts two formats.

The simple format is a mapping of scenario names to option dicts:

```json
{
   "scenario": {
      "heavy": {"max_urls": 10}
   }
}
```

The multi-step format is a list of steps. Each step is a single-key
mapping of a scenario name to its options. This runs the steps in
order, each in its own browser session:

```json
{
   "scenario": [
      {"full": {"max_urls": 150}},
      {"settled": {"max_urls": 100, "max_tabs": 50}}
   ]
}
```

A step can also include a **prefs** key. These preferences are appended
to the profile's `user.js` before the browser starts for that step:

```json
{
   "scenario": [
      {
         "full": {"max_urls": 150},
         "prefs": {"dom.storage.enabled": true}
      }
   ]
}
```

### Overriding a customization

Instead of a name or a path, the `--customization` argument also
accepts a JSON object. The optional **customization** key names the
base file; the remaining keys are overrides applied on top of it:

```json
{
   "customization": "default",
   "max_urls": 100,
   "prefs/some.pref.timeout": 0,
   "scenario": [{"full": {"max_tabs": 5}}]
}
```

A key containing `/` is an exact [dpath](https://pypi.org/project/dpath/)
path into the file, and creates the leaf if it does not exist. A key
without `/` is matched against every leaf with that name, wherever it
sits, and every match is replaced. When an override replaces the
**scenario** list, each new step inherits the options of the base step
with the same scenario name. A key that matches nothing is added at the
top level and a warning is logged, since that usually means a typo.

When **customization** is omitted, the base is the `DEFAULT_CUSTOMIZATION`
declared by the scenario module, if any.

Profiles built from an override object are cached under a hash of the
object rather than under the base name, so different overrides never
share an archive.

For example, to build the `qm_init` scenario with 50 origins and a
dirty shutdown:

```
$ ./mach run-condprofile --scenario qm_init \
    --customization '{"max_urls": 50, "dirty_shutdown": true}' /tmp/archives
```

### Local profile cache

Profiles downloaded by `condprof.client.get_profile` are kept in
`~/.condprof-cache`, named by `get_profile_archive_name`. Passing
`run_local=True` to `get_profile` only looks there and raises
`ProfileNotFoundError` on a miss, with no network access.

Harnesses that build profiles on the fly use
`condprof.runner.get_or_build_profile`: it returns a cached profile when
one exists for the scenario and customization, and otherwise builds it
with `Runner`, starting the scenario's proxy if it declares one, and
saves the result into the cache through
`condprof.client.save_profile_to_cache`. Delete the archive from
`~/.condprof-cache` to force a rebuild.

The mitmproxy binaries for a scenario's proxy are downloaded by mozproxy
to `<dir>/testing/mozproxy`, the same place every other harness keeps
them. `<dir>` is the `--proxy-dir` argument (`proxy_dir` for `Runner` and
`get_or_build_profile`); `mach run-condprofile` defaults it to the objdir,
which `mach raptor` uses too, and in automation mozproxy derives it from
`MOZ_UPLOAD_DIR`. Without any of these a temporary directory is used and
the binaries are fetched again on the next run.

### Example

In this example, we install uBlock, set a pref, and pass the
**max_urls** option to the **heavy** scenario.

```json
{
   "name": "intermediate",
   "addons":{
      "uBlock":"https://addons.mozilla.org/firefox/downloads/file/3361355/ublock_origin-1.21.2-an+fx.xpi"
   },
   "prefs":{
      "accessibility.tabfocus": 9
   },
   "scenario": {
      "heavy": {"max_urls": 10}
   }
}
```
